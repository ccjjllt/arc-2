## 2 对 015 原始结果的独立复算

18 次任务调用恰好为 6 次 high 和 12 次 low；全部有 usage。14 次 length 且 final 为空，1 次 stop 且 final 为空，3 次 stop 且 final 是合法网格。合法最终答案率是调用层面的 3/18，得到至少一个合法答案的 query 为 2/6。不能把 15 次无最终答案简单写成 15 道不会解的题。

| 策略 | 实际 completion token | 实际波次墙钟 | 合法输出 / 调用 | 已有评分 |
| --- | ---: | ---: | ---: | ---: |
| T-high，一次 xhigh，32K 上限，C2 | 155733 | 4106.13 秒 | 1/6 | 1/6 |
| T-low，两次 low，各 16K，C4 | 186047 | 2234.37 秒 | 2/12 | 1/6 |
| 全部三次调用 | 341780 | 6340.50 秒 | 3/18 | 原候选并集 2/6 |

安装加加载 658.3 秒；会话总计 7009.1 秒。两档最大 completion 预算相同，不代表实际 token、墙钟或算力相同。high 的 3 个波次聚合吞吐为 31.49、35.98、45.68 tok/s；low 为 75.46、87.33、86.76 tok/s。不能把 C2/C4 的差异都归因于 reasoning effort，也不能用 hello 的速度替代长请求测量。

high 命中 `58c02a16_0`，总 completion 为 **15941**，低于 low 的 16384 上限。该事实只能支持“本次 xhigh/seed1001 样本完成并命中，low 两份未完成”，**不能证明增加上限到 32K 是命中原因**。effort、seed、并发均不同。

low 在 `db118e2a_0` 的两份网格相同。本次以专用 `experiments/012/inputs/p2-scoring.json` 独立确认两份都是逐格精确命中。`58c02a16_0` 的合法网格和调用身份已复核，精确命中沿用 015 已有评分记录；未为了重复评分打开混合真值文件。其余 query 没有 final，按原口径留在分母并记错。

`db118e2a_0` 的 high 在 8720 token 正常 stop，但 final 空。reasoning 末尾已逐行构造 15×15 输出，最后停在讨论输出标签的半句。原始 SSE 摘要没有保存具体 stop token ID，无法确定是 EOS、标签交互还是其他停止原因。它适合补一次 final 恢复诊断，不能径直归因于 token 上限或求解能力。

## 3 并集能否变成实际两个槽

本次人工 CPU 重放固定规则：按 `T-high → T-low seed2001 → T-low seed2002` 遍历，只保留合法 final，按网格内容去重，再取前两份。P6 每个 query 实际至多只有一个不同的合法网格，所以这个**不读取答案的规则**确实保留全部既有命中。只有一份时重复填第二槽、零份时用合法兜底即可形成两个槽。

因此，既有产物上的固定规则回放可记为 **2/6**（其中 58 的命中继承 015 评分）。它比“只能报 oracle 并集”更具体；但它仍是开发集离线回放，不是新 GPU 实验、未见确认、公榜成绩或全量可运行方案。三个调用最大合计 65536 token/query，不能把它标成 32K 策略。其他题一旦出现三个不同候选，这个顺序可能丢掉正确解，仍须报告真正两个槽。

## 4 12 小时预算：原配置不能直接放大

以下全部是**场景算术，不是全量实测**。本笔记沿用本次 setup 658.3 秒，并留 600 秒落盘余量；主计划采用更保守的 0.5 小时启动＋1 小时整体余量＋10.5 小时生成，执行以[主计划](../../docs/plan/016-budgeted-final-submission.md)为准。两种预留口径不能直接混算。query 数由隐藏输入实际读取；240、280、340 仅是调度场景，不当作已取得的隐藏 query 数。

按既有每 query 波次成本线性外推：

| query 数 | 既有 high 策略 | 既有 low 策略 | 既有三调用混合 |
| ---: | ---: | ---: | ---: |
| 240 | 45.97 小时 | 25.18 小时 | 70.80 小时 |
| 280 | 53.58 小时 | 29.31 小时 | 82.54 小时 |
| 340 | 64.98 小时 | 35.52 小时 | 100.15 小时 |

high 目前 C2 含波次末尾空闲，改 C4 有潜在吞吐收益但尚未测量。即便用已测 C4 的 75–87 tok/s，把 12 小时扣掉上述 setup 与余量，允许的平均**总 completion**预算也只有：

| query 数 | 75 tok/s | 87 tok/s | 每 query 一次总 8192 token 的预计总时长 |
| ---: | ---: | ---: | ---: |
| 240 | 13107 token | 15204 token | 7.63–6.63 小时 |
| 280 | 11234 token | 13032 token | 8.84–7.67 小时 |
| 340 | 9252 token | 10732 token | 10.67–9.24 小时 |

未另建模不同输入长度的 prefill、长上下文减速、调度尾部、异常恢复，故这些是粗略可行性窗口，不能作运行保证。按 75 tok/s，先给每 query 一个 8K 样本后，理论剩余最多只容纳约 60%/37%/13% 的 query 再给一个同长样本；实际要更少。若想人人两个 16K 样本，当前实测吞吐不支持。第二个答案应选择性分配，或来自更便宜且已验证的互补方法。

## 5 下一次最小实验

### A. 先利用已有推理，诊断能否交出答案

重用 15 份没有合法 final 的完整 reasoning（high 5 份、low 10 份），不重跑长推理。每份只追加一次 `enable_thinking=false`、固定 seed、最多 4096 completion token 的 final 请求；输入为原题面及该份 reasoning 的固定尾部，要求只交最终网格。保留原有 3 份合法 final。固定使用末尾 16000 字符或先冻结的 tokenizer token 尾部上限，不按答案挑选思考片段；字符上限不等于 token 上限。

可借用已有公开实现 `madarshbb-b98k-v1.source.py` 的 `RESCUE`/`answer`，以及 `russcore.source.py` 的 `recover_grid`。借的是“读取自己的推理笔记再强制给 final”这一小段，不搬整个 agent 框架。

报告每臂恢复后的完成率、EM@2、上述固定混合规则的真实两槽结果、新增及丢失，并保存前后原文。恢复成本最多 61440 新输出 token，额外 prompt/prefill 与安装仍另计。**部署评价必须加回原 341780 token、6340.5 秒推理成本**；不能因为 replay 便宜就把长推理混合说成 12 小时可用。

### B. 再做真正面向提交预算的短思考

先维持同一权重/引擎/TP4，C4，对冻结 P6 比较相同总预算的 low 与 xhigh，各每 query 一次、统一固定 seed：总上限 8192，其中思考约 6144、最终输出预留约 2048。每臂报 EM@1，两个臂的固定混合报 EM@2；实验让每题都运行两臂是为了比较，部署仍应是一遍覆盖加选择性第二遍，不能直接搬成人人两个 8K 样本。先验证 native thinking budget 真生效，再开始 P6，不要服务拒绝后默默去掉预算继续烧满。

当前代码只有 `reasoning_effort` 模板提示，没有 `thinking_token_budget`，也没有服务端 `--reasoning-config`。本轮[方法研究](methods-research.md)已查固定 commit 的参数、配置和 sampler 链路，当前版本可从 Qwen3 parser 自动推导边界，无需因旧公开实现使用显式 `--reasoning-config` 就机械追加。固定 wheel 的实际生效路径仍需一次极小预算的真实请求确认，不能因源码有字段就称已启用。不同时增加 MTP、FP8 KV、C16/C24 或换框架。

30×30、空格分隔、单个无语言 fence 的 ASCII 最终网格共 1807 字符。主代理随后已用固定缓存 tokenizer 做 CPU 序列化计数：该协议 1803 token，紧凑行 933，紧凑 JSON 1801，默认带空格 JSON 2700，见[实际计数](evidence/final-space-token-counts.json)。2048 final 储备对严格网格协议有容量依据；总 max_tokens 仍包括强制结束标记和 EOS。计数不保证模型不额外解释，也不保证所有 final 都完整，不能把字符数与 token 数混用。

原 prompt 要求模型自行写 `<think>` 标签，模板也已开启 thinking。首轮可保持题面不变以隔离预算机制；若删掉这句标签指令，须记录为新配置，不能把结果全部归因于预算控制。若终止后仍没有有效 final，再使用最多一次短 recovery，并计入总成本。

P6 比较得到完整答案及新增后再扩 P12；配置冻结后才使用主 C6 一次。P6 已开发多轮，不能当泛化证明。若完成率提高但没有新解，才把下一份预算给现成 `transform(grid)` 的完整程序生成与一次 demo 执行反馈；不先恢复大规模 SFT/TTT。
