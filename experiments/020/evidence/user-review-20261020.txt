## 二、当前最严重的缺陷在哪里？

### 1. 正式 Notebook 可能一直解错输入文件

当前 full Notebook 会把所有 `*challenge*.json` 排序，再选择第一个结构合法的文件。实际日志中的顺序是：

`evaluation → test → training`

所以 pilot 选择了 `arc-agi_evaluation_challenges.json`，而 **full Notebook 保留了相同逻辑**。正式运行时也可能继续解公开 evaluation，生成错误任务集合的提交文件。

**必须显式区分公开演练与正式提交，正式模式只读取唯一匹配的 `arc-agi_test_challenges.json`。** 这个修改优先级最高。[待提交 Notebook](https://github.com/ccjjllt/arc-2/blob/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/submit/notebook/arc2-019-submit-full.ipynb) · [实际选文件日志](https://github.com/ccjjllt/arc-2/blob/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/submit-pilot/kaggle-v1/arc2-019-p1-pilot.log)

### 2. 第二阶段浪费了已经生成的完整程序

第二阶段先等待整批 `chat_wave` 结束，之后才执行程序。

这次有 **8 份程序已经正常生成**，合计 **72,253 token**；但主线程一直等到全局截止，才开始执行它们。结果全部 `exec_seconds=0`，没有产生任何程序候选。

应直接复用第一阶段已有的逐结果回调：

**每份程序返回 → 立即解析 → 执行示例与 query → 入候选池 → 写盘。**

我已经用原执行器、原资源限制，对这 8 份原始程序完成 CPU 重放，结果是：

- 4/8 能输出合法 query 网格；
- **0/8 query exact**；
- 其余出现索引错误、类型错误，以及 `frozenset` 不在允许 builtin 中的问题。

所以调度必须修，但**这 8 份现有程序没有可立即回收的新增正确解**，不需要再花 GPU 重新生成它们。[第二阶段程序与运行记录](https://github.com/ccjjllt/arc-2/tree/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/submit-pilot/kaggle-v1/vprobe/S2) · [提交驱动](https://github.com/ccjjllt/arc-2/blob/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/submit/vdriver019_submit.py)

### 3. 提交版本的“修复”请求漏掉了原程序

P4 驱动已经把 P0 代码加入反馈提示，但 **submit 驱动没有同步**。它只发送“原始题面＋执行反馈”，没有发送 `p0["parsed"]["code"]`。

模型不知道被反馈的程序具体是什么。即使跑满 11 小时，这也无法复现 018 已验证过的修复条件。应直接携带**完整 P0 代码＋真实示例反馈**。[反馈构造位置](https://github.com/ccjjllt/arc-2/blob/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/submit/vdriver019_submit.py)

### 4. 算力分配和候选选择仍然过于粗糙

目前“选择性程序”的条件包含 `attempt_1 == attempt_2`。第一阶段每题只产生一个候选，随后复制到两个槽，所以 **172/172 全部进入程序阶段**。

另外，候选池在示例得分相同时，固定优先 `program_fix > program_init > direct_grid`。因此两个 **0 个示例正确**的程序网格，也能把已有直出候选全部挤掉。

应该改为：

- 未覆盖题先获得有效候选；
- 全示例已过的程序停止昂贵修复；
- 接近正确的程序进入局部修正；
- 明显错误的规则进入独立新假设；
- 选择依据示例证据和候选差异，不能仅按“来自程序”优先。[分配逻辑](https://github.com/ccjjllt/arc-2/blob/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/submit/vdriver019_submit.py) · [候选池排序](https://github.com/ccjjllt/arc-2/blob/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/submit/submit_lib.py)

### 5. 文档的“C8 串行”判断错误，会把下一轮带偏

我按每条请求的发出、完成时间重算：

- 最大同时在途请求：**8**；
- 平均同时在途请求：**约 7.88**；
- 单请求平均耗时：**约 172 秒**；
- 整体生成吞吐：**144.12 token/s**。

文档用 `3756 秒 ÷ 172 次 = 21.8 秒` 推断并发为 1，混淆了**流水线完成间隔**和**单请求时延**。C8 已经真实并发，不应再为“恢复并行”开实验。安装加载总计也应是 **662.5 秒**，其中已经包含安装时间，不能重复相加。[请求时间证据](https://github.com/ccjjllt/arc-2/blob/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/submit-pilot/kaggle-v1/vprobe/run.json)

## 三、下一轮研究应该专注于什么？

**重点已经从“能否输出闭合程序”，转向“程序的规则是否正确，以及如何便宜地修正它”。**

本轮有一个很有价值的具体证据：`F-aa` 虽然 **0/3 示例 exact**，但 **1,468/1,519 个格子正确，约 96.64%**。它的外围扩张使用四邻域；在 CPU 上仅把这一处改为八邻域，三个示例就全部通过。

这是训练示例上的人工诊断，没有把补丁后的 query 记成新增解；而且该题已经被 R 解出。它支持研究的机制是：

> **对已有完整程序做少量、受限的语义参数修正，再用全部示例共同筛选。**

例如四／八邻域、排序方向、旋转方向、局部平移等。每次只改变有明确错误依据的少量参数，限定候选数与 CPU 时间。这里的“接近正确”也要看形状、发生变化的格子和错误位置，不能只依赖容易被背景色抬高的总体格子准确率。[F-aa 程序](https://github.com/ccjjllt/arc-2/blob/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/p4/kaggle-v1/vprobe/P6plus4/F-aa4ec2a5_0.code.py) · [正确的 R-aa 程序](https://github.com/ccjjllt/arc-2/blob/92eb44c69ae1d3ea98b13cf26fc742cd0a593778/experiments/019/p4/kaggle-v1/vprobe/P6plus4/R-aa4ec2a5_0.code.py)

对应的下一轮路线应当是：

| 程序状态 | 下一步 |
|---|---|
| 示例全过 | 保存候选，应用到该 task 的全部 query |
| 局部规则接近正确 | 优先有限 CPU 参数搜索，必要时一次反馈 |
| 运行异常、接口不兼容 | 修正明确的执行问题，并重跑全部示例 |
| 输出基本无效、规则明显不成立 | 独立生成不同假设，避免整段反复修补 |

**不要把“示例 exact 为 0”简单等同于必须重启，也不要把“程序能解析”简单等同于值得花 9K token 修复。**

## 四、我建议下一轮这样执行

**第一，立即完成提交链的局部修复。** 固定正式输入文件、S2 逐结果执行落盘、F 携带 P0、修正补题选择和候选优先级。这些已经有明确代码位置，不需要再建设框架。

**第二，暂停当前 `low／2K thinking／4K total` 直出配置的全量扩跑。** 本次 0/158 已经提供了足够的否定证据。保留历史有效提交作为保底，新的 27B 路线需要先证明实际增益。

**第三，下一笔 GPU 预算只回答一个问题：在相同总成本下，“独立候选＋局部 CPU 修正＋选择性反馈”能否增加最终两个槽的正确题数。** 固定开发题与候选选择规则，整批一次运行，避免再次围绕已解出的 291、aa 做演示。

**第四，程序按 task 复用。** 同一个规则生成、验证一次后，应应用到该 task 的全部 query。当前按 query 分别写程序，像 `13e47133`、`142ca369` 都重复生成了同一任务的程序，增加了费用。

**第五，不再把“跑满 11 小时”设为交付前提。** 修正后根据实际 query 数、实测吞吐和当下额度安排运行；先形成有准确率证据的候选，再增加覆盖和预算。下一轮交付必须同时有：**可正确读取正式输入的 Notebook、实际输出、固定双槽准确率、净新增题数和完整成本**。

**现在最值得加速的是从已有错误中提取可复用的修正机制，并把正确候选及时兑现到提交文件。继续扩大当前零正确的直出配置，或者无差别给所有程序追加一次反馈，都缺乏本轮证据支持。**
