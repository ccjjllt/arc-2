# 014：013 提交退分的独立源码审计

日期：2026-10-17，北京时间。范围：只读比较 `013/baseline-audit` 与 `013/submission-src`，读取已有普通运行事件，手动 CPU 预算算术；未运行 GPU、未读取确认题答案、未修改求解代码。本报告由主代理并行审计子任务产出。

## 结论与证据边界

013 **不是只修运行稳定性的等价版本**。它同时改变了训练实际更新数、每批搜索时间、搜索覆盖、救援和最终第二答案的选择规则。最值得怀疑的是“训练时间按任务预算 40% 截断”和“剩余推理时间再均分到所有增强批次”共同压低了解题强度，而 4 题 pilot 未模拟隐藏全集的调度压力。

这只证明存在足以造成退分的机制，**不能单凭源码把公榜下降归因到其中某一项**。本子任务未取得 submission 57103498 的隐藏日志/候选；精确分数由主代理查证。`baseline-audit` 是 latest v21，**不是历史 30.14 对应的 scriptVersionId 314617319**。没有那份精确源码，就不能称为“30.14 版本与 013 的单变量对照”。

当前 `submission-src` 的 solver、loader、builder、supervisor、pool SHA 与 `kaggle-baseline-verified-v1/013-code` 一致。loader 和 decoder 在 v21 审计目录与 submission-src 间完全相同；decoder 本身没有被打包进冻结运行，实际使用独立 builder。

## 最强风险一：pilot 与隐藏调度不同

supervise:101–102 将隐藏求解总额度设为 43,200 − 600 = 42,600 秒；setup、加载等也消耗这段时间。pilot 只有 4 题，4 worker 每题都拿到 1200 秒。

手动从源码 AST 提取 `compute_puzzle_budget` 进行纯算术，详见 `regression-budget-scenarios.json`。以 **240 题、已用启动时间 360 秒、首个弹出任务**为条件：

- 每题预算 `(42600−360)×4/(239+4) = 695.31 秒`。
- 训练额度为 `695.31×0.4 = 278.12 秒`，只相当于 pilot 的 480 秒上限的 57.9%。
- 训练若用满额度，第一批 DFS 的理论准入时间：单 query 78.22 秒、双 query 39.11 秒、三 query 26.07 秒。尚未扣除训练后切换、tokenize 等开销。
- 名义 `ARC_DFS_TIME_LIMIT=540` 是另一个上限；实际常由上述更小值决定。

这不是每个隐藏任务都恒定 695 秒：其他任务提前完成后，后续预算会增大；首批不同 worker 的排队数也不同。这里也没有断言隐藏任务数已由日志证实。若 120 题，首题封顶 1200 秒；若 400 题，同样启动条件下首题约 419 秒，训练约 168 秒。

## 最强风险二：DFS 截得太短时，完整候选直接消失

013 DFS 只返回走到 EOS 的完整输出（solver:235–243、275–291），没有在截止时保存可续算的搜索状态。原有 min_prob 0.20 对应的是累计序列 NLL 门槛 `-log(0.2)`，并非每个 token 独立 20% 门槛。这一门槛没改，但更短 TTT 可能降低整条正确输出的概率，同时更短 DFS 可能来不及走完长输出；两种影响会叠加。

多 query 任务在相同题预算下要除以更多批次。预算也没有按输出长度/前缀长度分配。同一批内多个长度 bucket 又从长到短共用截止（solver:306–307），第一个 bucket 可以占满本批时间，后续 bucket 没机会执行。这些都是源码可见机制，但隐藏出现次数未知。

## 最强风险三：评分可能吃掉后续批次额度

solver:601–603 的“公平份额”**只作用于 DFS**。随后每个候选的 `check_deadline` 和 `calc_scores` 使用的是 **整个 puzzle_deadline**（618、645–647），不是该批的份额截止。默认不限制 scored beams（supervise:139）。

因此，首批产生较多独特候选时，8 视角 NLL 重评分可能消耗远超预留 30 秒的时间，留给后面视角/query 的时间缩短，极端时后续 query 没有真实候选。已经完成生成但未完成全部 NLL 的候选不会保存；原子落盘只保护已完成评分的候选。

这是一项具体的调度设计缺陷/风险，不能写成已证实隐藏故障。pilot 的完整 beams 总数与已存候选数都是 92，没有观察到该小样本发生“生成完成后评分丢失”；不能据此排除全集风险。

## 没有找到的明显 bug，以及容易误判的点

- 未发现 query 序号偏移或颜色逆变换新增 bug。split_multi_replies 和 invert_mod 实现未改，query 键的归组方式在单 task 内等价。
- 新 builder 的 `support − mean(score_aug)` 与原 `score_kgmon` 公式一致；排序方向、去重和 tie-break 一致。013 既有人工 CPU 记录中 1000 组对照一致。本审计没有为相同检查新增测试。
- v21 的救援/多样性选择确有不可靠处，但删掉它们也删掉了可能有用的候选。消除一个可能有害因素不等于最终分数必然更高。
- 5/5 query 有候选、无损坏文件只证明小样本运行成功；不证明隐藏全集覆盖，也不证明候选正确，更不证明恢复了 30.14。
- `train_done.metrics.train_steps_per_second` 在中途停止时可能用计划步数作分母/分子口径；例如 75 实际步/474.08 秒约 0.158 步每秒，记录里的 0.27 不宜直接用于预测实际训练进度。应使用真实 `trained_steps` 和阶段时间。

## 最值得马上验证的三件事

1. **恢复精确证据，而不是凭结果猜。** 获取 57103498 的隐藏 worker 日志、coverage、训练步数分布、fallback、每 query 生成/评分/选中计数；如果 Kaggle 不提供隐藏产物，明确注明无法直接归因。并尽力获得历史 314617319 精确源码，不能用 latest v21 替代。
2. **做现实预算的少量同题配对。** 用已使用的开发题、相同数据/种子/模型/选择器、约 700 秒任务预算，优先对照训练完成度与 DFS 批次分配；记录实际步数、完整候选覆盖和 pass@2、时间。保留原 30.14 结果；不要以第二次完整公榜提交代替本地消融，也不要只重复 1200 秒的 4 题宽松 pilot。
3. **将“生成不了”和“选错了”分开。** 在有答案的开发题保存真实原始完整候选及评分完成状态，再离线比较候选上限与最终 pass@2。重评分、beam 概率、救援来源保持分离；必要时单独限定评分预算/分阶段选择，不能把未评分候选伪造为已评分。下一次实现应围绕已验证瓶颈，而非继续同时改多种算法。

本审计不能支持任何具体提分承诺；它支持把 013 视为发生了研究性退步的新配置，尽快做因果定位，并让新的 27B 高吞吐方向与基线诊断并行。
