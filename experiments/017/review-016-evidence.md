# 017 前置复核：016 v1 原始证据

日期：2026-10-19，北京时间。只读复核 016 已运行产物、远端实际源码与当前本地副本；没有运行 GPU、提交、修改求解代码或新增测试。评分仅按固定 P6 白名单解码本地答案对应条目，不读取 C6/981 答案。本笔记供主代理修订研究记录与 017 计划。

## 1 需要修正的实质口径

### 1.1 527390 token 不是 R 恢复策略成本

原始 [016 run.json](../016/kaggle-v1/vprobe/run.json) 与逐请求 usage 独立加总一致：

| 范围 | completion token |
| --- | ---: |
| 016 C4 | 8192 |
| 016 C8 | 8192 |
| 016 R | 36637 |
| 016 B8 | 42649 |
| 016 B16 | 89940 |
| 016 B 合计 | 132589 |
| 016 全部主实验，59 次 | **185610** |
| 016 预热及探针，17 次 | 512 |
| 016 全部76次 | **186122** |

185610 不含辅助512，低于主实验上限225280；186122低于含辅助上限225792。记录中的这个部分正确。

但 `527390 = 341780（015全部任务调用）+185610（016全部主实验）`，混入了 C4/C8 与 B，不能放在 R 表内当恢复策略成本。R 使用原18个样本、只补15份失败时，累计 completion 应为 **341780+36637=378417**，不含两轮辅助请求。若要报告015/016所有请求的研究总量，两份 run 中分别是341994与186122，合计 **528116**；527390可以保留，但必须明确“两个研究会话的主实验输出总量”。

时间同理：`7945.3 = 6340.5 + (2271.4−666.6)`，后项包含016的全部非安装加载时间，不能称R推理累计。仅累计015任务推理与R阶段为 **6340.5+351.74=6692.24秒**；加载与其他阶段另列。

### 1.2 配额2.15小时不能归因于本作业墙钟×2

016 `elapsed_s=2271.4`，按历史2倍配额规则算术为 **1.261889配额小时**，不是2.15。`2.15/(2271.4/3600)=3.408`，因此“+2.15h≈墙钟×2”数值不成立。

持久化 [push.json](../016/execution/push.json) 只有事前四舍五入的 `used_h=18.35`、`remaining_h=11.65`。本次在016产物中未找到事后20.50/9.50的原始账户响应或带查询时间的独立余额快照。文档中的20.50与9.50可标为既有文字记录、待重新查询；不能当作已经持久核实的隔离作业账单。即使补齐账户前后差，也须说明间隔内其他作业/平台记账情况未排除，不把差值全部归因于本次运行。

### 1.3 `preempt_total=0` 是日志关键词计数，未测真实事件计数器

远端实际 [vdriver016.py](../016/kaggle-v1/016-crb-code/vdriver016.py:129) 的 `count_preempt` 实现是：

`count("preempt") + count("recompute") + count("preemption")`。

没有采集服务 metrics 中真正的累计抢占/重算计数；`preemption` 若出现还会被两个子串重复计数。本次服务日志的三个词均未出现，所以得到0。它支持“**未见抢占/重算日志**”，不支持“测得实际抢占/重算次数严格为0”。全部请求有usage且正常返回、未见OOM日志，仍支持本次会话运行稳定的结论，不需为这项计量缺口单独重跑GPU。

### 1.4 123.41是这份暖缓存混合队列的有效吞吐

`132589/1074.4=123.40748`，B摘要中的 **123.41 tok/s**算术正确。分子是B8/B16的12请求全部completion，分母是整份混合队列墙钟，包含该阶段prefill与尾部降并发；不是单请求速度求和，也不是满C8稳态速度。

B阶段日志107个采样中：Running8为66个、Running2为25个，其余为7/6/4/3/1。B的TTFT范围0.21–1.71秒，开始前相同题面已被预热、C对照和R访问；该阶段累计prefix命中率约57.4%。R的169912输入token对应TTFT为4.91–39.65秒，明显不同。

因此123.41可作有明确条件的预算参照；程序提示、较长prefill、P2最初只有两条可运行P0、以及依赖P0的后续分支，不保证达到该速率。017不宜用它作为无折扣的会话完成保证或预算硬拒绝依据。

### 1.5 新增合法数量需使用配对口径

- B8合法4/6，B16合法6/6；B16相对B8**新增合法query为2个**，是291和4c。B16“5个合法错解”是其全部错误合法输出数，不是相对于B8新增5个。
- R为8次stop+合法、7次length+非法。7次截断包括4c×3、58-low×2、**aa-low×2**；016结果文字只列了前5次。
- 这两处不改变EM结论，但会夸大新增完成量或遗漏失败。

`6661−6144=14853−14336=517`，两题均输出16×16空格数字网格，相同形状会有相同输出token数量；硬思考预算加等长final是与证据一致的解释。无需因为两个数字相同就否定运行结果。

## 4 C4/C8和容量证据

两份C摘要和逐请求usage一致：C4/C8各16次、各8192completion、各67306prompt token；墙钟93.28/52.16秒，`S=1.788`，聚合87.82/157.07。C4日志9个采样都Running4，C8日志5个采样都Running8。真实八路存在，暂选C8有本轮证据。

仍是统一预热后的单次C4→C8顺序实验。服务日志累计prefix命中率在C4段约68.8→76.6%，C8段约79.9→81.5%；这些是累计比率，不能误读为每阶段独立命中率，也不能因此直接反算缓存造成多少提速。长生成没有C4配对重跑，不能把短测1.788移给长程序。

日志KV占用采样峰值：C4短测4.4%、C8短测6.7%、R29.1%、B16.5%。启动容量704876token/65536=10.76×是容量估算，不是性能保证。016文字“最坏约27%”是旧场景算术，R实际采样已到29.1%；应以实测描述，不称理论上安全。

证据：[C4-summary](../016/kaggle-v1/vprobe/C4-summary.json)、[C8-summary](../016/kaggle-v1/vprobe/C8-summary.json)、[服务日志](../016/kaggle-v1/vprobe/vllm-server.log)。
