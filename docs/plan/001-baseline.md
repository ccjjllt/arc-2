## 目标与假设

1. 核实 2026 赛程、评分、提交要求、GPU 使用限制及奖牌规则。
2. 判断 L4×4 与 v5e-1 的训练适用性，不把硬件可运行等同于能够提分。
3. 读取指定 Notebook 的代码、依赖、输入权重、日志与对应 submission，明确实际基线。
4. 建立用户要求的研究交接文档，不建设自动化测试体系。

待验证假设：该 Notebook 可能沿用 NVARC 的预训练权重及部分推理组件；标题不足以确认其具体实现。若已含测试时训练（TTT），后续研究应优化已有配置与数据，不能把再次加入 TTT 当作新贡献。

## 调研与手动实验方案

本轮首先进行只读调研。读取现有配置时只确认服务可用性，凭据仅用于对应 Kaggle 服务的正常认证，不写入文档或日志。

取得指定版本后，整理：

| 项目 | 需要记录的内容 |
| --- | --- |
| 来源 | Notebook owner/slug、scriptVersionId、上游来源 |
| 模型 | 基础模型、权重与 adapter 的数据集版本、训练数据覆盖 |
| 求解路径 | TTT、候选生成、增强、PoE/重排、TRM/程序搜索是否实际运行 |
| 预算 | GPU 使用方式、阶段耗时、每题耗时、超时/漏跑题数 |
| 输出 | submission 与日志的位置、生成答案数量 |
| 成绩 | 具体 submission、计分时间、公榜/私榜口径与名次 |

后续由人工发起少量题的诊断，再视需要完整复现。固定任务列表和配置，保存逐题输出、耗时与汇总。公开题如已用于训练，只能作为机制诊断；不要声称它们能估计未见题泛化。
