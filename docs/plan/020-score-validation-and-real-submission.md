### 4.1 原程序M0/M1对照设计（已完成，结果为负）

以下是已执行的原始设计，保留作成本和研究结果的解释。两项策略在原D24匹配query上均0/34，不能据此继续原样扩跑。当前C24确认的是冻结Direct1的绝对准确率；固定CPU线段补充器适用0题，因此M0/M1文件来自同一首稿，不是两项独立策略或增益比较。

- **M0 独立候选**：P0 + 一次独立R，按固定demo证据选两槽。
- **M1 选择性修正**：相同P0 → 有限CPU局部修正；未解决且近似时至多一次F，明显失败时使用同一独立R；全demo通过则停止修复。选槽不看query真值。

沿用已跑通的程序参数：`xhigh / thinking=8192 / max_tokens=12288`，P0种子5101、F种子5103；独立R采用明确不同的种子5105，并冻结采样参数。R只看题面，不看P0、反馈或另一分支结果。所有分支输出完整通用 `transform(grid)`，禁止task ID查表和硬编码已知query答案。

两项部署策略各最多两次GPU调用；对照研究共享P0，需要F的题额外生成R用于比较，整批最多三次调用/task，即 **24×3×12,288＝884,736输出token**。这只是生成上限，不是3小时必跑完的承诺；跨账号分片不增加调用次数或token上限。共同P0、各分支增量、部署总成本、整场研究账本分别记录；CPU成本也计入M1。

单会话先覆盖全部task的P0，再排第二次调用；分片时在各固定子集内遵循同样顺序。同批F/R顺序交错，避免一臂总在截止前被饿死。达到阶段总求解预算仍未完成时，保存结果与原定分母，缺失记失败/未完成；不只挑完成题比较，也不把partial写成正式通过。分片成本与额外加载按第2节单列。

### 4.2 记录与决策

原程序对照报告最终 **EM@2**、相对M0新增/损失query与task、全demo通过率、合法程序率、真实候选覆盖、不同双槽数、占位数、生成但未选中正确候选的数量，以及完整时间/token/配额账本。候选池oracle只诊断选择损失，不作为提交得分。当前Direct1确认报告固定分母EM@2、真实预测/占位、格式失败、时间/token与CPU适用情况；Direct1没有执行demo程序，其demo exact记未知，不能沿用程序路线的0-demo字段作失败率。

D24用于确定政策，不要求M1必须赢。按用户最新要求，重点报告实际新增/损失query、不同task的表现及完整成本，不再把“净增2个query、至少2个task”设为进入确认的硬门槛。少量成功保留为研究线索，选出较强且成本可承担的策略继续确认；若两项都无真实正确解，依据负结果调整研究方向，避免原样扩大该配置。

C24前已冻结Direct1加CPU线段补槽的代码、输入、prompt、种子、每task预算、选槽和停止条件，按全清单一次运行。所有分片输出落盘并固定SHA之后才统一评分。CPU在C24适用0题，不能由本次确认声称CPU相对Direct1有增益或无泛化价值；也不再根据两个同源M0/M1文件作优劣选择。不能看C24答案改政策再重新称它确认集。

### 4.3 运行中暴露的问题：连续思考与重启的预算对照

本小节同样保留已执行设计；DeepP0固定匹配评分为0/8，实际合法query输出1/9，未支持扩大原程序深首稿配置。后续长思考直出同时改变表示和预算，开发结果与成本另记，不将其当成本节的等上限消融。

首片12次调用没有全部demo通过；原始reasoning中多份以半句或未完成的规则假设结束，随后进入代码。尚未逐条用tokenizer计数，不能称每条恰好耗尽8192，但该现象支持另一个具体研究问题：同一总输出上限，连续较深推理是否优于两次短推理。它不证明更长一定有效，也不把27B当前配置当能力上限。

在读取本轮D24 query答案前，从原D24每个S/M/L层按`sha256(20261020:DeepP0:+task_id)`取最小两题，冻结[DeepP0清单](../../experiments/020/deep-p0/manifest.json)：6task/9query，保留所有query。只追加一次P0，`max_tokens=24576 / thinking=16384 / seed=5101`，复用现有两次`12288/8192`的M0产物，不重跑旧臂。两种政策的每task最大completion allowance均为24576；实际token和运行时间独立记账，不能称实际成本相等。题面、提示、权重和选槽规则保持相同，深首稿只提供实际选出的两槽，不合并旧臂形成oracle政策。

这是小规模开发研究，不占用或提前读取C24。按首片约98token/s，最多147456新token，预计含安装加载约40分钟；新会话上限1小时，优先使用ccjjllt余量，最多约2.3配额小时，单列新增加载成本。研究首稿模式不用于正式提交。短机械反馈与此对照回答不同问题：前者检验廉价修复，后者检验首稿思考分配。根据实际正确解与成本确定后续政策，避免无证据升级全部题的预算。

**这组对照只能证明同一27B方法间的差异，不能证明胜过历史30.14。** 本轮不额外重开4B GPU基线。可在CPU修复阶段限时查找历史精确版本；取得源码不等于复现，未取得不阻塞27B首个有效计分实验。未来组合基线与27B时，必须比较实际选出的两个槽，不能拿各自两槽的四候选oracle冒充组合成绩。

## 5 如何尽快形成可提交版本

当前候选来源固定为一次长思考P0直接输出该task全部query网格，加统一按demo筛选的CPU线段规则。每query至多一个P0网格和一个CPU网格，去重后最多两格，保留P0；没有CPU候选时两槽重复P0。程序F/R及有限程序修复保留为已结束的研究记录，不进入本次Direct1政策。多query任务仍按task生成一次，全部query一起保存。

开发已出现正确解，C24运行期间D的普通CPU保存已完成：`ccjjllt/arc2-020-deep-direct-submission` v1 / scriptVersionId `360461153`，详见[核验记录](../../experiments/020/execution/final-save-verified.json)。C24结果返回后据实判断并发起正式提交，不再重开已知负配置。最终Notebook固定两种运行模式：

- 普通Save & Run：`public_eval`，完整公开evaluation输入初始化，运行固定CPU规则，300秒；实际预测、占位和未进行模型推理分别记录。
- `KAGGLE_IS_COMPETITION_RERUN`明确为真：`competition_submit`，只读正式test全集，同一C24的27B direct1+CPU补槽，41400秒（11.5小时）总盒，距平台12小时留30分钟。

普通CPU分支仅满足平台保存与产文件需要；实际隐藏模型、候选选择、每task上限与C24冻结政策相同，只有全局预算变化。正式模式不挂载D24/C24答案或公开答案，不依赖已解题ID特判。环境标记在013已有使用记录；缺省标记为普通模式，出现非预期非空值明确失败，不能静默退回evaluation。

普通运行由Notebook内部300秒总时钟结束，**最终版本不能保存短平台timeout**。本次push显式请求`--timeout 43200`，用于容纳隐藏41400秒；不把300秒普通预算写成平台会话上限。CLI到`session_timeout_seconds`的请求映射已核实，但远端metadata/status不返回该字段，43200秒尚无独立回读证据。

## 6 真正提交怎样完成

**`kaggle kernels push`成功、Notebook COMPLETE、生成submission.json，都不等于比赛已提交。**

1. D结束后保存实际Notebook owner/slug、版本号、`scriptVersionId`、源码/权重/输入/输出SHA、运行日志和最终选槽结果。取回输出，确认task/query键与对应输入一致，两个attempt均合法。
2. 查询实际提交身份的每日额度和pending/scoring状态；规则与当前可提交状态以平台返回为准。保留历史30.14，不擅自改最终两份候选选择。
3. 使用已完成的**精确版本**发起代码竞赛提交，让平台重跑隐藏test；不要把公开evaluation预测当静态比赛答案上传。CLI 2.2.4源码已核对，下面形式调用代码提交接口：

   ```bash
   kaggle competitions submit arc-prize-2026-arc-agi-2 \
     -k <实际owner>/<实际冻结slug> \
     -v <D的实际版本号> \
     -f submission.json \
     -m "020 frozen Qwen3.8-27B direct1 + CPU line"
   ```

   owner必须是实际可提交且已核实的Notebook owner；版本号不能用latest代替。当前CLI `-k/-v`已核实可用，不采用旧第三方源码“不能用--kernel”的注释作为操作依据。API等价路径必须同样绑定固定版本。
4. **成功返回submission ref，并在比赛提交列表再次看到该ref及关联版本**，才记“已正式提交”。把记录写入 `experiments/020/execution/competition-submission.json`。请求超时先查列表，避免不确定状态下重复提交。
5. 后续由执行者查询该ref直至COMPLETE或明确失败；PENDING不等于出错，也不代表已开始GPU运行。记录public_score/error、时间和来源；私榜尚未开放就写未确认。此处是执行交接，不自动创建轮询或提醒任务。

提交目的按证据诚实命名：若只有相对旧27B的增益，称 **首个27B有效计分实验**；只有新正式public_score大于30.14，才称 **超过历史公榜最高**。拿牌取决于最终排名，不能用C24比例或公开集分数保证。

在有实际正确解、冻结版本成功运行和预算证据后，尽快发出这次计分实验，不等局部修正“完美”。结合Direct1的开发与确认结果判断候选；普通CPU保存成功本身不证明模型有效。若仍未形成有效候选，或输入/截止仍不正确，就据实报告未提交原因，不能为了形式重投25.69或提交已知0/158原配置。
