### 4.1 只比较两项可部署策略

- **M0 独立候选**：P0 + 一次独立R，按固定demo证据选两槽。
- **M1 选择性修正**：相同P0 → 有限CPU局部修正；未解决且近似时至多一次F，明显失败时使用同一独立R；全demo通过则停止修复。选槽不看query真值。

沿用已跑通的程序参数：`xhigh / thinking=8192 / max_tokens=12288`，P0种子5101、F种子5103；独立R采用明确不同的种子5105，并冻结采样参数。R只看题面，不看P0、反馈或另一分支结果。所有分支输出完整通用 `transform(grid)`，禁止task ID查表和硬编码已知query答案。

两项部署策略各最多两次GPU调用；对照研究共享P0，需要F的题额外生成R用于比较，整批最多三次调用/task，即 **24×3×12,288＝884,736输出token**。这只是生成上限，不是3小时必跑完的承诺；跨账号分片不增加调用次数或token上限。共同P0、各分支增量、部署总成本、整场研究账本分别记录；CPU成本也计入M1。

单会话先覆盖全部task的P0，再排第二次调用；分片时在各固定子集内遵循同样顺序。同批F/R顺序交错，避免一臂总在截止前被饿死。达到阶段总求解预算仍未完成时，保存结果与原定分母，缺失记失败/未完成；不只挑完成题比较，也不把partial写成正式通过。分片成本与额外加载按第2节单列。

### 4.2 记录与决策

必须报告：最终 **EM@2**、相对M0新增/损失query与task、全demo通过率、合法程序率、真实候选覆盖、不同双槽数、占位数、生成但未选中正确候选的数量，以及完整时间/token/配额账本。候选池oracle只诊断选择损失，不作为提交得分。

D24用于确定政策，不要求M1必须赢。完整对照中，M1至少净增2个query、涉及至少2个task且成本可承担，才作为值得确认的方法增益信号；这是预算分配阈值，不是统计显著性或奖牌预测。若M1无净增，直接选择较强的M0；若两项都无真实正确解，结束该配置的GPU扩跑，保留额度和失败记录。

C24前冻结代码、输入、prompt、种子、路由阈值、每task预算、排序和停止条件，再一次运行两策略。输出落盘并固定SHA之后才评分。确认中有净增才保留M1的“增益”判断；持平或退步优先简单且较省的M0。不能看C24答案修阈值再重新称它确认集。

**这组对照只能证明同一27B方法间的差异，不能证明胜过历史30.14。** 本轮不额外重开4B GPU基线。可在CPU修复阶段限时查找历史精确版本；取得源码不等于复现，未取得不阻塞27B首个有效计分实验。未来组合基线与27B时，必须比较实际选出的两个槽，不能拿各自两槽的四候选oracle冒充组合成绩。

## 5 如何尽快形成可提交版本

候选来源统一为通用程序P0、有限CPU修正、独立R与条件F。当前低预算直出不再作为强制全量第一阶段。每个task先有一次机会，再按示例证据分配剩余预算；已通过全部demo的程序立即应用全部query并保存。多query任务的成本按task生成和query执行分别计量。

C24有正确解后进入D。最终Notebook预先固定两种运行模式：

- 普通Save & Run：`public_eval`，完整公开evaluation，4小时总时间盒。
- `KAGGLE_IS_COMPETITION_RERUN`明确为真：`competition_submit`，只读正式test全集，11小时总时间盒，距平台12小时上限仍留1小时。

两种模式使用相同模型、程序方法、候选选择及每task上限，只允许输入和全局预算按已声明政策变化；正式模式不挂载D24/C24答案或公开答案，不依赖已解题ID特判。环境标记在013已有使用记录，仍须本地手工验证两分支。缺省标记为普通模式；仅按核实过的真/假取值映射，出现非预期非空值就明确失败，不能静默退回evaluation。

普通4小时由Notebook内部总时钟结束，**不要未经核实就给最终冻结版本加 `kernels push --timeout 14400`**。CLI会把该值保存为 `session_timeout_seconds`，是否约束隐藏重跑未确认；平台会话上限应足够11小时及收尾，避免正式运行被保存的4小时上限截断。

D必须读取全量task/query并初始化完整文件，真实覆盖与占位分开报。4小时不能完成全部求解时，记录实际尝试数；不能声称“全量输入”即“全量已推理”。根据本次 **程序长请求** 的吞吐、输入长度及CPU执行成本估算隐藏预算，不沿用直出的144 token/s作保证。

供人工算账：若有240 task，两次12,288上限调用需5,898,240输出token；聚合150 token/s约10.92小时，尚未计安装和CPU，不能承诺11小时装得下。100 token/s则仅生成就16.38小时。因此11小时策略必须先保证一轮P0机会，再选择性追加；使用实际N和剩余时间动态控制准入。记录输入最慢一档任务，不再重犯013小片长预算外推隐藏规模的错误。

若D暴露确定性运行错误，先修再冻结新版本；用预留额度做必要的有限重跑，原错误版本不得提交。若只是M1不优于M0，使用已冻结的M0，不再追加一轮方法搜索。

## 6 真正提交怎样完成

**`kaggle kernels push`成功、Notebook COMPLETE、生成submission.json，都不等于比赛已提交。**

1. D结束后保存实际Notebook owner/slug、版本号、`scriptVersionId`、源码/权重/输入/输出SHA、运行日志和最终选槽结果。取回输出，确认task/query键与对应输入一致，两个attempt均合法。
2. 查询实际提交身份的每日额度和pending/scoring状态；规则与当前可提交状态以平台返回为准。保留历史30.14，不擅自改最终两份候选选择。
3. 使用已完成的**精确版本**发起代码竞赛提交，让平台重跑隐藏test；不要把公开evaluation预测当静态比赛答案上传。CLI 2.2.4源码已核对，下面形式调用代码提交接口：

   ```bash
   kaggle competitions submit arc-prize-2026-arc-agi-2 \
     -k <实际owner>/<实际冻结slug> \
     -v <D的实际版本号> \
     -f submission.json \
     -m "020 frozen Qwen3.8-27B program candidate"
   ```

   owner必须是实际可提交且已核实的Notebook owner；版本号不能用latest代替。当前CLI `-k/-v`已核实可用，不采用旧第三方源码“不能用--kernel”的注释作为操作依据。API等价路径必须同样绑定固定版本。
4. **成功返回submission ref，并在比赛提交列表再次看到该ref及关联版本**，才记“已正式提交”。把记录写入 `experiments/020/execution/competition-submission.json`。请求超时先查列表，避免不确定状态下重复提交。
5. 后续由执行者查询该ref直至COMPLETE或明确失败；PENDING不等于出错，也不代表已开始GPU运行。记录public_score/error、时间和来源；私榜尚未开放就写未确认。此处是执行交接，不自动创建轮询或提醒任务。

提交目的按证据诚实命名：若只有相对旧27B的增益，称 **首个27B有效计分实验**；只有新正式public_score大于30.14，才称 **超过历史公榜最高**。拿牌取决于最终排名，不能用C24比例或公开集分数保证。

在有实际正确解、冻结版本成功运行和预算证据后，尽快发出这次计分实验，不等局部修正“完美”。若两策略及确认都无正确解，或输入/截止仍不正确，就明确报告“未形成有效候选、未提交”，不能为了形式重投25.69或提交已知0/158原配置。

## 7 提交后如何服务奖牌目标

首个27B榜分到手后，按同一队伍的历史30.14比较。若低于历史分，保留历史候选并检查运行覆盖、候选生成和选槽损失；拿不到隐藏日志时不编造原因。若高于历史分，优先继续已验证的新增来源，并研究与可复现基线的实际双槽互补，不立即重启大规模微调。

另行读取当日官方公榜名次及奖牌规则，记录抓取时间；不得沿用10月12日或17日的分数线冒充实时门槛。官方页面当前列最终截止为 **2026-11-02 23:59 UTC，即北京时间11月3日07:59**，入队/合并截止为北京时间10月27日07:59。提前提交给排队与故障留下时间，截止前保留两份实际计分且具有互补证据的最终候选；最终选择由用户决定。
